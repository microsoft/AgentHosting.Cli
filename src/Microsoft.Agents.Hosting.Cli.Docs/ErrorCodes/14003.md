# 14003: Existing target agent ownership is unverified

[All error codes](../ErrorCodes.md)

## What happened

An agent already uses the intended schema name in the target environment, the project's workspace is still connected to an agent outside its record's home environment, or a workflow would be deployed over one that an environment outside its record's home environment already holds. The CLI stopped without pushing because the project cannot establish that this deployment owns it.

## Why this happens

When attaching or retargeting a workspace, the CLI looks up the schema name. Automatic adoption requires matching recorded ownership or deployment history. A matching name alone is not permission to replace another agent.

A project cloned from another environment stays connected to its source agent until its first deploy to its home environment creates its own agent. A dev deployment in the source environment would push to that source agent, replacing its content and, when the clone declares a new name, its name, so the CLI holds it to the same rule: the record must name the agent, or the deployment must have deployed it before. Test and Prod deployments overwrite it without asking, as they overwrite drift.

A standalone workflow cloned from another environment keeps its source's workflow ID, and a deploy writes by that ID. A dev deployment outside the record's home environment that never deployed the workflow would therefore replace the content and name of the workflow that environment already holds, such as the clone's source, so the CLI refuses it. Test and Prod deployments replace it without asking, and a dev deployment whose environment does not hold the workflow creates it.

## How to fix it

Inspect the cloud agent or workflow ID and the environment in the error. Confirm who owns it and preserve any cloud changes before proceeding.

Only if replacing that agent or workflow is intentional, repeat the MCS `msagent agent deploy` command with `--overwrite`. This accepts adoption and replacement of its content and name; it is not merely a retry switch. Once that deploy succeeds, the record names the agent, or the deployment has deployed the workflow, so later deploys to the same deployment need no flag. Alternatively, use `--schema-name` with an appropriate name this project owns to deploy an agent separately.

For the source agent of a clone, `--schema-name` does not help, because the workspace stays connected to that agent. To leave it untouched, deploy to the dev deployment in the agent's home environment instead, which creates the clone's own agent there.

A workflow has no schema name, and its clone keeps its source's ID wherever it is deployed. To leave the environment's workflow untouched, deploy to a deployment in another environment, such as the dev deployment in the workflow's home environment.

## How to avoid it

Retain project deployment records and use distinct schema names for unrelated agents. Review adoption carefully when moving between environments or restoring a project. Deploy a clone from another environment to its home environment before any deployment in its source environment, and give a workflow clone no dev deployment in its source environment unless it should replace the source.
