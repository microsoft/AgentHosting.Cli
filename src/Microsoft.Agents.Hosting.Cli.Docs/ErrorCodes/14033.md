# 14033: AMS operation was rejected or unconfirmed

[All error codes](../ErrorCodes.md)

## What happened

AMS rejected an agent, deployment, deploy, channel, or OAuth connection request, or returned an agent, agent-list, package-list, deployment, deployment-list, channel, channel-type, Direct Line token, channel webhook, OAuth provider, or OAuth connection response that the CLI could not validate. The CLI also reports this code when a deployment is being deleted, or when a channel or OAuth command names a deployment that was never deployed.

## Why this happens

The accompanying message distinguishes authentication, authorization, service failures, records that changed since they were read, names already in use, deployments that cannot be deployed yet, deployments being deleted, refused deletions, and refused channel and OAuth connection requests. A success HTTP status can also lead here if the response cannot describe the expected agent, deployment, channel, channel types, token, webhook values, OAuth providers, or OAuth connection.

## How to fix it

Follow the specific remediation rather than repeating every request:

- For `deployment-lifecycle-unavailable`, AMS does not support that code-agent command in that environment yet (it answered HTTP 501, or HTTP 404 without an AMS error code on a route only newer AMS versions serve), and nothing changed. msagent does not fall back to another route. The AMS release that serves that environment does not support the command yet; ask the AMS team when it will.
- For `agent-changed` or `deployment-changed`, someone changed the agent or deployment after msagent read it, and AMS changed nothing. Run the command again; it reads the current record first.
- For `agent-not-found` or `deployment-not-found`, AMS has no such agent in the home environment or no such deployment of the agent; an earlier delete may already have removed it. Check the ids and that `--environment-id` (which defaults to the active environment) is the agent's home environment. Create a missing deployment with `msagent deployment create`.
- For `agent-name-in-use` or `deployment-name-in-use` (exit code 2), another agent of the environment, or another deployment of the agent, already uses the name; the message names it. Choose another name.
- For `invalid-field-value` (exit code 2), AMS refused a value of the request and the message gives its reason. Correct the option it names. A dev endpoint must be an HTTPS dev tunnel URL (`*.devtunnels.ms`) of a `dev` deployment in a target environment enabled for dev endpoints.
- For `agent-deleting`, the agent is being deleted, so AMS refuses new deployments and deploys of it. Finish the deletion with `msagent agent delete`, or use another agent.
- For `deployment-deleting`, the deployment is being deleted, so it cannot be changed or deployed. Finish the deletion with `msagent deployment delete`, or with `msagent agent delete` when the whole agent is being deleted. The message names the deployment when AMS reports it.
- For `agent-deployment-conflict` from `deployment create`, the target environment already has a deployment of this agent with other settings: `msagent deployment list` shows it. Put it live with `msagent agent deploy`, or delete its record first. From `agent deploy`, the hosting runtime of the target environment still holds another deployment of this agent or of its Entra application, possibly from a deleted record: use a deployment in another target environment, or delete the agent with `msagent agent delete`.
- For `package-required`, the agent has no package upload to deploy. Upload one with `msagent agent package upload`, then deploy again.
- For `commit-not-found` (exit code 2), no upload of the agent has that commit. `msagent agent commit list` lists the commits.
- For `prod-needs-test`, AMS deploys the newest upload to Prod only after a Test deployment of the agent runs it. Deploy it to a Test deployment first, then deploy Prod again.
- For `agent-bot-service-app-id-in-use`, AMS could not create the deployment's bot, because Azure Bot Service allows one bot per application id and another bot uses the deployment's Entra application id. Remove that bot (when the deleted deployment record of an AMS agent kept it, `msagent agent delete` of that agent removes it), then deploy again.
- For `deployment-delete-unavailable`, AMS does not delete code-agent deployment records in that environment yet (it answered HTTP 501), and nothing was deleted. The AMS release that serves that environment does not delete deployment records yet; ask the AMS team when it will.
- For `agent-deploy-in-progress`, a deploy of one of the agent's deployments is still running, so AMS cannot finish deleting the agent yet. The message gives AMS's reason; run `msagent agent delete` again at the time it names. Until then the agent stays marked for deletion.
- For `agent-bot-service-deletion-failed`, AMS could not confirm that it deleted a bot, so the agent stays marked for deletion. Run `msagent agent delete` again; it resumes where it stopped.
- For a bot that does not belong to the deployment (`agent-bot-service-conflict`), do not retry. Give the correlation IDs to the AMS team; the deployment, or the agent delete, stays refused until then.
- For `deployment-not-deployed`, a channel or OAuth command named a deployment that was never deployed, so it has no bot whose channels or OAuth connections can be managed. Deploy it first with `msagent agent deploy`.
- For `deployment-has-no-bot`, AMS has no Azure Bot Service instance for the deployment, so it has no channels or OAuth connections to manage. Check the deployment's bot with `msagent deployment show`; AMS creates one at the first deploy of a code-agent deployment with an App Registration or Blueprint identity.
- For `invalid-channel-request` (exit code 2), AMS refused the channel request and the message gives its reason, which names only fields, channels, and list items by their site name, page id, or registration id. Correct the request; `msagent deployment channel types` lists the channel types, operations, and parameters AMS accepts. When `deployment channel token` reports it, no site of the deployment's Direct Line channel could issue the token; a new bot can list no site until its Direct Line channel is first updated. List the sites with `msagent deployment channel show --channel directline`, then pass a usable one with `--site`, add one with `msagent deployment channel update --channel directline --add-site siteName=<name> isV3Enabled=true`, or turn one on with `--set-site siteName=<name> isEnabled=true isV3Enabled=true` instead of `--add-site`.
- For `channel-settings-refused` (exit code 2), Azure Bot Service refused the credentials or settings of the channel, and AMS changed nothing. The message never contains a credential. Check the values in `--parameters` against the third-party console (for example the Telegram token, or the Twilio account id, auth token, and phone number), then retry.
- For `invalid-oauth-request` (exit code 2), AMS refused the OAuth connection request and the message gives its reason, which never contains a secret. Correct the request; `msagent deployment oauth list-providers` for the same deployment lists the providers and parameters AMS accepts.
- For `channel-not-found` (exit code 2, as in local mode), the deployment's bot has no such channel. Create it with `msagent deployment channel create`, or list the channels with `msagent deployment channel list`.
- For `oauth-connection-not-found` (exit code 2), the deployment's bot has no OAuth connection with that name; names are case-sensitive on AMS. Create it with `msagent deployment oauth create`, or list the connections with `msagent deployment oauth list`.
- For `directline-unavailable`, AMS issues Direct Line tokens only for bots in the `global` location, in clouds where it has a Direct Line endpoint, and no token was issued.
- For `channel-operation-failed`, Azure Bot Service or Direct Line was unavailable or refused the operation AMS sent. A change may still have reached the channel, so check it with `msagent deployment channel show` before you retry; if it fails again, give the correlation IDs to the AMS team. Azure Bot Service also answers wrong Facebook credentials this way, so when a Facebook create or update keeps failing, check the app id, app secret, page ids, and page tokens first.
- For `oauth-operation-failed`, Azure Bot Service was unavailable or refused the OAuth operation AMS sent. A change may still have reached the connection, so check it with `msagent deployment oauth show` before you retry; if it fails again, give the correlation IDs to the AMS team.
- For sign-in or access failures, correct the account, environment, or permissions first.

For invalid responses or an indeterminate change, inspect authoritative state using the correlation IDs before retrying. A remote change may already exist.

## How to avoid it

Use compatible service contracts, read records shortly before changing them, and coordinate concurrent changes to the same agent or deployment.
